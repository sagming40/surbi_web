## 📌 프로젝트 상시 규칙

> 날짜에 종속되지 않고 **지금도 유효한** 규칙·방침만 모읍니다.
> 규칙이 바뀌면 이 블록을 **덮어쓰고**, 바뀐 경위는 해당 날짜 일지에 남깁니다.

### 개발 체제
- Frontend는 **1인 개발 구조**로 분리됨 (담당: 사공민규)
- 팀장 지침: 개별 개발 후 **주간 정기회의에서 진행상황만 공유**

### 브랜치 전략
- **(2026-08-03 변경)** 1인 프론트 독립 개발 체제 확인 → PR 승인 절차 없이 **main 직접 작업 허용**
- 화면 전체 리팩터링 · 실험적 시도(디자인 A/B 등)는 롤백 지점 확보를 위해 임시 브랜치 권장
- 브랜치를 쓸 경우, **새 브랜치는 항상 최신화된 `main`에서 분기할 것** (스태킹 방지 원칙은 유지)

### 커밋 규칙
- `feat:` 화면/기능 신규 구현 / `style:` 시각적 디테일 조정 / `fix:` 버그 수정 /
  `refactor:` 출력은 동일하되 구조 개선
- `git commit -m "요약" -m "설명"` 형식 (한국어 요약 + 영어 스타일 본문)
- 렌더링 성공 · `flutter analyze` 통과 등 **안전 지점 도달 시 커밋**
- 성격이 다른 변경은 **커밋 단위를 분리**할 것
- **(2026-08-20 추가)** 커밋을 나누는 기준은 **파일 수도 줄 수도 아니라 '목적 수'다.**
  git은 줄 단위로 담을 수 있으므로(GitHub Desktop은 diff 왼쪽 체크박스) 파일 하나도
  여러 커밋으로 쪼갤 수 있다. 다만 **수단과 목적을 갈라놓으면 안 된다.**
  - 나누면 안 되는 예: "색을 화면마다 다르게 주려고 파라미터를 추가"한 변경을 `refactor`와
    `style`로 분리 → 중간에 **아무도 안 쓰는 파라미터를 만든 커밋**이 남아 이유를 알 수 없게 됨
  - 나눠야 하는 예: "구조만 바꾸고 동작은 그대로"인 변경이 **독립적으로 의미 있을 때**
    (리뷰어가 동작 보존을 따로 검증할 수 있음)

### Git 환경
- **(2026-08-20 추가)** 윈도우 작업 환경은 `git config core.autocrlf true`를 반드시 설정한다.
  미설정 시 줄바꿈(CRLF↔LF)만 다른 파일 전체가 변경으로 잡혀 **실제 변경이 묻힌다.**
  - 진단법: `git diff --ignore-all-space`가 **비어 있으면** 내용 변경 0 = 줄바꿈 문제
- `.git/index.lock`은 git이 "지금 저장소 작업 중"임을 알리는 임시 팻말이다. 비정상 종료 시
  남을 수 있고, 남아 있으면 커밋이 `A lock file already exists`로 거부된다.
  **git이 돌고 있지 않을 때만** `Remove-Item .git\index.lock -Force`로 삭제할 것

### 설계 원칙 (B안 원칙)
- **View 계층에 데이터 하드코딩 금지.** 모든 상태는 Provider 계층에 격리
- Provider 종류 선택 기준:
  - 단순 조회용(변경 없음) → `Provider`
  - 사용자 상호작용으로 실시간 변경(체크박스 토글 등) → `StateNotifierProvider`
  - 원본에서 파생되는 계산값(진행률 등) → **별도 파생 Provider**로 분리
    (View에 계산 로직이 들어가지 않도록)
- **PR 제출 전 View 파일에 하드코딩 값이 없는지 최종 검색** (재발 방지 체크리스트)
- **(2026-08-20 추가)** 스크립트로 생성한 데이터 파일은 **`lib/data/`에 격리**하고 손으로
  수정하지 않는다. 생성 출처·검증 방법·폐기 시점(TODO)을 파일 헤더 주석에 남긴다.
  (수백~수천 건 규모의 데이터를 provider 파일에 직접 두면 로직이 데이터에 파묻힘)

### 공용 위젯 사용 원칙
- 카드형 UI → **`SurbiCard`** (Container + BoxDecoration)
  - Material 3의 `Card`는 `surfaceTintColor`를 자동으로 덧씌워 지정 색이 탁해짐
- 화면 상단 → **`SurbiAppBar`**
- 도입 배경: 매 작업마다 "카드를 어떻게 만들지" 새로 판단하면 스타일이 미묘하게
  달라지고 같은 함정에 반복해서 걸림 → **검증된 디자인 결정을 코드에 고정**
- **(2026-08-20 추가)** 공용 위젯은 **특정 화면의 사정을 알지 않는다.** 위젯은 상태 변화
  (열림/닫힘 등)만 콜백으로 통지하고, 그 신호로 무엇을 할지는 사용하는 화면이 결정한다.
  - 예: `SurbiDropdown.onMenuVisibilityChanged` → 지도 화면만 이 신호로 지도를 잠근다.
    위젯 안에 지도 코드를 넣으면 지도가 없는 화면도 지도를 알아야 하는 구조가 됨
- **(2026-08-26 추가)** 시각 값은 **디자인 토큰에서만** 가져온다. 화면 파일에 색·모서리·
  그림자·글자 크기를 직접 적지 않는다. (`lib/app/theme.dart`)
  - `SurbiColors` 색 / `SurbiRadius` 모서리 / `SurbiShadow` 그림자 / `SurbiText` 글자 크기
  - 마우스 상호작용(hover·pressed·focus)은 **테마 루트에서 한 번만** 정한다
    (`ThemeData.hoverColor`·`highlightColor`·`focusColor`·`splashColor`).
    ⚠️ 단, `IconButton`은 `ThemeData.hoverColor`를 **읽지 않는다** — M3에서
    `IconButtonTheme.overlayColor`로 갈렸으므로 둘 다 지정해야 화면 전체가 같아진다
  - ⚠️ **Material 3는 `elevation > 0`이면 배경에 `surfaceTint`를 자동으로 덧씌운다.**
    배경색을 직접 지정한 곳에는 반드시 `surfaceTintColor: Colors.transparent`를 함께 적는다.
    하루에 같은 함정을 4곳에서 밟았다 — `SurbiCard` · `SurbiAppBar`(`scrolledUnderElevation`도
    같이 0으로) · `SurbiDropdown` 메뉴 · 지도 컨트롤 버튼
  - ⚠️ **`Colors.transparent`는 색이 아니라 "그리지 마라"는 뜻이다.** 색을 일괄 치환할 때
    이것까지 회색 토큰으로 바꾸면 **없던 선이 생긴다** (선택 안 된 탭 전부에 밑줄이 그려져
    구분선과 겹쳐 이중선이 된 사고)
  - ⚠️ **grep은 "틀린 색"은 찾아도 "빠진 색"은 못 찾는다.** 토큰을 도입한 뒤에는 화면을
    눈으로 훑어 확인하는 단계가 반드시 따라와야 한다
  - ⚠️ 토큰 이름에 **방향을 담지 않는다.** 점수는 높을수록 좋고 폐업 위험도는 높을수록
    나쁘다 → `high`/`low`가 아니라 `good`/`warn`/`bad`로 짓는다

### 테마와 상속 (2026-08-26 추가)

- **`Theme`은 명령이 아니라 상속이다. 상속은 언제나 가장 가까운 조상이 이긴다.**
  앱 최상단(`main.dart`)에 값을 박아두면 앱 전체에 적용될 것 같지만, 중간에 누가
  같은 종류의 Theme을 한 겹 더 씌우면 **거기서 끊긴다.**
  - 사례: `IconButtonTheme`을 `main.dart`에 두었는데 AppBar의 뒤로가기만 회색으로
    hover했다. Material 3의 `AppBar`는 자기 `leading`·`actions`를 감쌀
    `IconButtonTheme`을 **스스로 만들어 씌운다.**
  - 해결: 위젯에 **직접** 준 값은 테마보다 언제나 세다. 다만 그러면 값이 두 곳에
    적히므로, 공유 상수(`SurbiOverlay.iconButton`)를 만들어 전역 테마와 위젯이
    **같은 것 하나**를 읽게 한다.
- **`IconButton`은 `ThemeData.hoverColor`를 읽지 않는다.** M3에서
  `IconButtonTheme.overlayColor`로 경로가 갈렸다. 둘 다 지정해야 화면 전체가 같아진다.
- **"맞춰야 할 속성이 두 벌"이면 위젯으로 합친다.** 속성 목록을 손으로 대조하는 한
  누군가 한쪽만 고치는 날이 온다.
  - 사례: `SurbiAppBar`와 `ExploreTopBar`가 각자 만든 뒤로가기 IconButton이
    아이콘 종류·크기·hover 원의 색과 크기·왼쪽 여백까지 전부 갈렸다
    → `SurbiBackButton` 하나로 합쳐 **맞출 것 자체를 없앴다.**
- **"통일"은 생김새가 아니라 규칙을 맞추는 것이다.**
  - 8/26 오전에 상단 바 배경을 본문과 같은 색으로 "통일"했더니 통일은 됐지만
    **어디까지가 바인지 안 보이게** 됐다. 맞춰야 했던 건 "같은 색"이 아니라
    "바는 어느 화면에서든 본문보다 한 톤 밝고 아래에 얇은 선을 둔다"는 규칙이었다.
  - 같은 이유로, 드롭다운에 넣은 윤곽선을 동 목록 22개에 똑같이 넣지 않았다.
    선을 넣은 이유는 "흰 바탕에서 흰 알약이 사라져서"였고, 그 문제가 없는 곳에
    같은 모양을 복사하면 규칙이 아니라 장식이 된다.

### 글자 크기를 '명시'해야 하는 때 (2026-08-26 추가)

> **"모든 `TextStyle`에 `fontSize`를 적어라"는 틀린 규칙이다.** 버튼 라벨이 버튼
> 테마를 타는 것은 정상이며, 거기에 크기를 박으면 나중에 테마에서 한 번에 바꾸는
> 길이 막힌다. 명시가 필요한 건 아래 세 경우뿐이다.

- **ⓐ 우리 코드가 그 크기에 의존할 때** — 하단 시트 CTA 버튼은 `fontSize`를 아예
  적지 않아 `ElevatedButton` 기본값(labelLarge 14)을 타고 있었는데, 바로 위의
  `height = 패딩×2 + 20`이 그 "14 × 줄높이 1.43 ≈ 20"을 가정하고 있었고
  `measureStops`가 그 height를 읽어 시트 높이를 계산했다.
  → **우리가 정하지 않은 값 위에 우리 계산이 얹혀 있었다.**
- **ⓑ 상속받을 부모가 없을 때** — 직접 그린 위젯(`TabBar`가 아니라 `Container`로
  만든 탭바)이나 우리 `Theme`을 보지 않는 외부 라이브러리(`fl_chart` 툴팁).
- **ⓒ 여러 곳이 같아야 하는데 각자 기본값을 탈 때** — `SurbiEmpty`·`SurbiError`·
  `SurbiLoading` 셋이 모두 미명시라 **"우연히" 같았다.** 한 화면이 다른 Theme
  아래 놓이는 순간 갈린다.
- ⚠️ 이 결함은 **grep으로 찾을 수 없다.** '틀린 값'이 아니라 '없는 값'이라서다.
  검색은 있는 것만 본다. `TextStyle(` 블록을 열어 `fontSize` 유무를 세는
  스크립트를 돌려야 나온다.

### 시각 표현 원칙 (지도·차트)
- **(2026-08-20 추가)** 한 시각 채널에 두 가지 정보를 싣지 않는다.
  **면(fill) = 데이터 / 선(stroke) = 구조와 선택**을 기본으로 삼는다.
  두 정보가 같은 채널을 놓고 겹치면 서로 채도를 깎아 둘 다 안 보인다.
- 무언가 **안 보일 때 대비부터 올리지 않는다.** 배경과 **색 계열이 같은 것**이 원인이면
  아무리 진하게 해도 "배경의 일부"로 읽힌다. 계열을 바꾸면 더 옅게 하고도 더 잘 보인다.
- 반투명 겹침은 계산으로 값을 정한다 — **아래 색이 남는 양 = (1 − 위쪽 불투명도) × 아래 불투명도.**
  두 값이 비슷해지면 색이 섞여 제3의 색으로 보인다.
- 값을 정했으면 **값만이 아니라 근거(계산식·실패했던 값)를 주석에 남긴다.**
  근거가 없으면 다음 사람이 "이 숫자 왜 이래?" 하고 되돌린다.
- **(2026-08-26 추가) 값이 비슷하다고 하나로 합치지 않는다. 기준은 "쓰이는 모양"이다.**
  회색 셋과 그림자 둘이 비슷해 보이지만 하는 일이 다르다.
  | 토큰 | 모양 | 왜 따로인가 |
  | --- | --- | --- |
  | `divider` #E5E9E9 | 화면을 가로지르는 **긴 직선** | 길어서 옅어도 눈에 들어온다 |
  | `border` #DAE0E0 | 알약을 감싸는 **짧고 굽은 선** | 같은 농도면 묻힌다 |
  | `placeholderGray` #D9D9D9 | 비활성·빈칸을 **채우는 면** | 넓어서 옅어도 보인다 |

### 레이아웃 계산 원칙

- **(2026-08-25 추가)** 위젯 높이를 코드로 계산해야 할 때는 **화면에 그려서 재려 하지 않는다.**
  화면 밖 복사본(`Offstage`)도 위젯 트리 안에 있는 한 부모의 크기 제약을 벗어나지 못한다.
  재려던 값이 원래 코드에 적어둔 상수라면, **그리지 않고 더하는 편**이 가볍고 안전하다.
  - 글자 높이만 `TextPainter`로 잰다 — `fontSize`는 글자 크기이지 줄 높이가 아니고,
    한글은 폴백 폰트를 타서 배수가 폰트마다 다르며, 폭이 좁으면 줄 수 자체가 달라진다
- **같은 숫자를 두 군데 적지 않는다.** 여백·문구를 `static const`로 한 번만 정의하고
  `build()`와 계산식이 **같은 상수를 읽게** 한다. 따로 적으면 한쪽만 고쳐도 컴파일이 통과한다.
  - 사례: `SurbiDropdown`의 메뉴 offset에 박혀 있던 `52`("버튼 높이에 맞춰 조정"이라는
    주석까지 붙어 있었다) → `collapsedHeight` 상수로 승격
- **`TextPainter`로 잴 때는 반드시 테마와 병합한다.** `Text` 위젯은 우리가 준 스타일만
  쓰지 않고 주변 `Material`이 깔아둔 `DefaultTextStyle`(= `theme.textTheme.bodyMedium`)과
  **병합해서** 그린다. Material 3의 bodyMedium에는 `height: 1.43`이 들어 있어,
  병합하지 않으면 제목 한 줄당 약 5px씩 짧게 나온다.
```dart
  final base = Theme.of(context).textTheme.bodyMedium ?? const TextStyle();
  TextSpan(text: text, style: base.merge(style))
```
- **(2026-08-26 추가) 테두리는 높이에 더해진다.** `Container`에 `decoration`의
  `border`를 주면 Flutter가 그 두께만큼 안쪽으로 패딩을 밀어넣는다.
  드롭다운에 1px 윤곽선을 넣자 높이가 52 → 54가 되어, 그 52를 읽는 하단 시트
  mid 계산이 2px 어긋날 뻔했다. 세로 패딩을 14 → 13으로 줄여 52를 유지했다.
- **(2026-08-26 추가) 같은 상수를 써도 결과가 같지 않을 수 있다 — 그 값이 어디에
  더해지는지까지 봐야 한다.** 상단 바 높이를 통일하며 두 위젯에 같은 규격을
  넣었는데, `SurbiAppBar`는 구분선이 `bottom:`이라 바 **바깥**에 붙고

  **안쪽**에 들어온다(`height 77`). 같은 77을 서로 다른 방식으로 만들어야
  눈에 보이는 결과가 같아진다.
- **계산이 틀려도 안 죽는 구조를 고른다.** 스크롤 가능한 한 겹(`ListView`) 안에서는

### 위젯 트리와 상태 수명

- **(2026-08-26 추가)** **조건부 `return`으로 트리 모양을 바꾸지 않는다.**
  Flutter는 위젯을 **트리 상 위치 + 런타임 타입 + key**로 식별한다. 타입이 같아도 위치가
  바뀌면 다른 위젯으로 보고 `Element`를 새로 만들며, 그때 거기 매달려 있던
  `State`와 `ScrollPosition`이 **통째로 버려진다.**
  - 사례: `if (!hasFooter) return list;` 다음에 `return Column([Expanded(list), footer]);`
    → 시트가 min 경계를 넘을 때마다 `ListView`가 **뿌리 ↔ Column의 자식**을 오갔다.
    `ScrollPosition`이 재생성되면서 그 위에서 돌던
    `DraggableScrollableController.animateTo`가 **중간에 죽어** 시트가 어중간한 높이에 멈췄고,
    드래그 때는 프레임마다 같은 일이 반복돼 시트가 떨렸다
  - 해결: **자리는 늘 지키고 내용만 비운다** —
    `Column([Expanded(list), if (hasFooter) footer else const SizedBox.shrink()])`
- **위젯에 넘기는 `List`·`Map`을 매 build마다 새로 만들지 않는다.** Flutter의
  `didUpdateWidget`은 대개 `!=`, 즉 **내용이 아니라 정체(identity)로** 비교한다.
  값이 똑같아도 매번 "바뀌었다"로 판정된다.
  - 사례: `DraggableScrollableSheet.snapSizes`를 getter로 매번 새로 만들었더니 내부
    extent가 프레임마다 교체돼 시트 크기가 `initialChildSize`로 되돌아갔다. 그런데 그
    되돌림은 컨트롤러 리스너를 울리지 않아 단계 값은 그대로 남았다 →
    **크기는 mid인데 내용은 min(헤더만)** 인 상태가 이렇게 생겼다
  - 해결: 필드로 들고 있다가 **값이 실제로 바뀔 때만** 새 리스트를 만든다
- **진실은 하나로 두고 나머지는 도출한다.** "크기 → 단계"와 "단계 → 크기"를 둘 다 쓰면
  한쪽이 낡은 값일 때 서로를 덮어쓴다. **크기가 진실**이고, 단계는 언제나 크기에서 계산한다.
- **build 도중에 컨트롤러를 만지지 않는다.** 이미 진행 중인 프레임 위에 레이아웃 요청이
  겹쳐 `Tried to build dirty widget in the wrong build scope`가 난다.
  `WidgetsBinding.instance.addPostFrameCallback`으로 프레임이 끝난 뒤로 미룬다.

### 제약(constraint)은 위에서 아래로 흐른다 (2026-08-26 추가)

- **부모가 tight 제약을 주면 자식의 `fixedSize`는 무시된다.** 자식은 부모가 정한
  크기를 따를 수밖에 없다. 위젯에 크기를 박아뒀다고 그 크기가 보장되지 않는다.
  - 사례: `SurbiBackButton`에 `fixedSize: 48×48`을 못박았는데 `/score`에서만
    hover 원이 컸다. `AppBar`가 `leading`을 두 번 옥죄기 때문이다 —
    가로는 `ConstrainedBox(tightFor(width: leadingWidth))`, 세로는
    `_ToolbarLayout`의 `loose(size).tighten(height:)`. 버튼 상자가 72×76이 되었고,
    `CircleBorder`는 **상자의 짧은 변을 지름으로 삼으므로** 원이 72로 그려졌다.
    (`ExploreTopBar`는 `Row` 안이라 loose 제약 → 48 그대로였다)
  - 해결: **`Center` + `SizedBox`로 한 겹 감싼다.** tight 제약이 그 껍데기에서
    끝나고, 껍데기가 늘어나 자리를 채우는 동안 안의 위젯은 정확히 원하는 크기를
    받는다. (물이 위에서 내려올 때 우산을 쓰는 것과 같다)
- **`AppBar`의 `leadingWidth` 기본값은 56이고, leading은 그 칸에서 가운데 정렬된다.**
  옆 화면이 "여백 + 버튼" 구조라면 중심이 어긋난다. 여백을 양쪽에 둔 폭
  (`gutter*2 + diameter`)으로 맞춰야 두 화면에서 같은 자리에 온다.

### Platform View(지도) 위의 Flutter UI

- **(2026-08-25 추가)** 지도 위에 얹는 Flutter 위젯은 **`PointerInterceptor`로 감싼다.**
  지도는 브라우저 DOM이라, 그 위에 위젯을 그려도 브라우저 입장에서는 지도가 여전히 거기 있다.
  휠·드래그 이벤트 하나가 양쪽에 배달된다.
- **`lockMap`(카카오맵 `setZoomable`/`setDraggable`) 방식은 한 박자 늦는다.** 지도 DOM의
  리스너가 먼저 실행되고 Flutter가 위젯에 전달하는 건 그다음이라 **첫 틱은 항상 샌다.**
  마우스를 움직여 들어오면 `onPointerHover`가 미리 막아주지만, 커서를 올려둔 채 휠만
  굴리면 그 방어가 비어 있다.
- 둘은 대체 관계가 아니다. `PointerInterceptor`는 **시트처럼 영역이 있는 위젯**에 쓰고,
  `lockMap`은 **`Overlay`로 뜨는 드롭다운 메뉴**처럼 시트 바깥 경로에 계속 필요하다.

### 조작 방식별 검증

- **(2026-08-25 추가)** 모바일 대상 화면을 **데스크톱 마우스 휠로만 검증하지 않는다.**
  Flutter의 `DraggableScrollableSheet`은 끌기와 휠을 다른 경로로 처리한다.

  → "휠로 되니까 된다"가 터치에서는 성립하지 않는다. 설계 전제로 삼기 전에 조작 방식을 구분할 것

### 겪었던 이슈들

**1. 경계가 안 보이던 원인은 대비가 아니라 색 계열이었다**
회색 경계가 지도에 묻혀 보이지 않았다. 처음엔 "연해서"라고 판단했지만, 카카오맵 밑그림 자체가
회색·흰색 톤이라 **회색은 아무리 진하게 해도 "지도가 그린 선"으로 읽혔다.** 네이비로 계열을
바꾸자 채움을 0.25 → 0.16으로 **오히려 낮추고도** 시인성이 올라갔다.

**2. 선택 동이 주황이 아니라 갈색으로 보였다 — 두 반투명이 비긴 것**
구 밑칠(네이비 0.16) 위에 선택 표시(주황 0.15)를 겹치자 색이 탁해졌다. 계산해보니
아래 색이 남는 양 = `(1 − 0.15) × 0.16 = 13.6%`로 주황 15%와 **거의 1대1**이었다.
주황이 이긴 게 아니라 비긴 것이었다. 주황을 0.35로 올리자 네이비는 10.4%만 남아
3대1 이상으로 벌어졌다. 값을 감이 아니라 계산으로 정하고, 식을 코드 주석에 남겼다.

**3. 같은 문제를 두 번 고쳐서 앞의 근거를 무너뜨렸다**
겹침 문제를 A안(주황 채움 제거)과 C안(네이비 면 낮추기) **둘 다** 적용했다. 그런데
A안만으로 이미 곱해질 상대가 사라져 해결된 상태였고, C안은 **흰 구분선의 전제를 깨버렸다.**
흰 선은 '선'이 아니라 **타일 사이의 틈**으로 기능하므로 나눌 면이 있어야 의미가 있는데,
면을 0.08까지 낮추자 밝은 지도 위의 흰 줄로만 남았다. 면을 0.16으로 되돌려 해결.
> 선택지를 나열할 때 **서로의 관계(A를 하면 C가 불필요해진다)를 함께 짚어야 한다.**

**4. 공용 함수를 고쳐 문제 없던 화면까지 망가뜨렸다**
`_renderBoundary()`는 Step 1과 업소 지도가 공용으로 쓴다. Step 1의 겹침 문제를 풀려고
채움을 0으로 만들자, **밑칠이 없어 애초에 문제가 없던 업소 지도**의 채움까지 사라졌다.
변경 전에 이 부작용을 인지했으면서도 "일단 통일"로 미룬 것이 원인이다.
파라미터 2개로 분기하고 기본값을 기존 동작으로 두어, 업소 지도 호출부는 한 글자도 안 고치고 복구했다.

**5. `.git/index.lock`이 남아 커밋이 거부됐다**
GitHub Desktop이 `A lock file already exists`로 커밋을 거부했다. 원인은 AI 보조 도구가
저장소 파일에 접근하는 통로에 **삭제 권한이 없어서**, `git status`가 만든 잠금 파일을
git이 스스로 지우지 못한 것. 로그에 `warning: unable to unlink index.lock`이 계속 떴는데
**경고라서 넘긴 것이 화근**이었다. 경고를 읽었으면 결과까지 따라갔어야 했다.

초기 화면이 밋밋해 서울 전역 행정동을 깔아봤다. 생성은 19~21ms로 §2 추정(44ms)보다도 빨랐지만
**드래그·줌이 무거워졌다.** 폴리곤은 만들고 끝이 아니라 지도 위에 남아 매 프레임 다시 그려진다.
Stopwatch가 재는 것은 "만드는 비용"뿐이고 "유지하는 비용"은 재지 않는다 — §2에서 로그에
적어둔 단서가 실제로 드러난 것이다. 자치구 25개로 바꾸니 렌더 4~5ms, 조작도 가벼워졌다.

**4. 구 경계를 새로 구하지 않아도 됐다**
자치구 경계 데이터가 없어 새로 확보해야 하는 줄 알았는데, 갖고 있던 동 경계를 구별로
합치면(dissolve) 그대로 구 경계가 됐다. 25개 전부 단일 폴리곤·구멍 없이 깔끔하게 나온 이유는
**8/20 오전에 mapshaper로 간소화할 때 topology를 보존**했기 때문이다. 인접한 동이 공유하는
선이 똑같이 깎여 있어 합칠 때 틈(sliver)이 생기지 않았다.

**5. 흰 구분선은 나눌 면이 있어야 의미가 있었다**
구분선을 흰색으로 바꾼 뒤 "면이 안 보이는데 왜 흰 선이냐"는 지적을 받았다. 흰 선은 '선'이
아니라 **타일 사이의 틈**으로 기능하는 기법이라, 채울 면이 옅으면 밝은 지도 위의 흰 줄로만
남는다. 게다가 카카오맵은 도로를 흰색으로 그려 헷갈렸다. `#9AA5B4`(네이비를 밝게 푼 계열)로
바꾸니 면과 톤이 맞으면서 카카오맵 자체 경계선과도 구분됐다.

없어졌고, **방어할 대상이 사라지자 방어 코드도 통째로 지워졌다.** 우회 코드가 늘어나고 있다면

화면과 함께 새로 만들어지므로 초기 상태에 머문다.
**상태를 화면에 잇는 코드에는 두 축이 모두 필요하다 — ①진입 시 1회 동기화 ②이후 변화 감지.**

원인은 `_paintBoundaries`가 `await` **앞에서 지우고 뒤에서 그렸기** 때문이다.
2-A에서 URL 동기화가 들어오며 이 함수를 부르는 경로가 **둘**이 됐고

```dart
final generation = ++_paintGeneration;   // 번호 뽑기
await Future.delayed(...);
if (generation != _paintGeneration) return;   // 내 차례 지났으면 물러남
_clearGuPolygons();                            // 지우기는 대기 '뒤'
```

같은 자리에 겹쳐 그려져 **눈으로는 알 수 없었고**, 성능 로그를 찍어두지

### 겪었던 이슈들

**1. 손잡이가 스크롤에 딸려 올라간 이유 — 커튼봉을 커튼에 꿰매둔 셈**

`SheetHandle`이 `ExplorePanel` 내부 `ListView`의 **첫 번째 항목**으로 들어가 있었다.
`ListView`는 자기 안의 모든 항목을 함께 밀어 올리므로 손잡이도 같이 올라간다.

`DraggableScrollableSheet.builder` 안에서 `Column`의 **형제**로 분리해 해결했다.
다만 손잡이를 스크롤 영역 밖으로 빼면 `DraggableScrollableSheet`가 오버스크롤을 감지하지
못해 **"손잡이 잡고 끌기"가 죽는다.** 그래서 `_dragSheetByHandle`(수동 `jumpTo`)와
`_snapSheetToNearest`(손 뗄 때 정렬)를 직접 구현했다.

덤으로 `SheetHandle`에서 `GestureDetector`를 걷어내 **순수 시각 위젯**으로 축소했다.
손잡이의 탭·드래그 처리는 `explore_page.dart` 한 곳에 모인다 — 8/20에 세운
"공용 위젯은 어떻게 생겼는지만 알고 누르면 뭐가 되는지는 모른다" 원칙 그대로다.

**2. ⭐ 자동 측정을 세 번 시도해 세 번 다 다른 이유로 실패했다**

min·mid를 화면 비율이 아니라 **실제 콘텐츠 높이**로 잡고 싶었다. 글자 크기는 화면 크기를
따라 커지지 않는데 비율만 화면을 따라가서, `min = 0.15` 같은 값은 작은 폰에서 헤더를 자르고
큰 화면에서는 남는다.

처음 택한 방법은 **"화면엔 안 보이지만 레이아웃 계산은 되는 그림자 복사본을 `Offstage`로
항상 그려두고 `GlobalKey`로 그 렌더 높이를 읽는다"** 였다.

| # | 시도한 구조 | 터진 에러 | 원인 |
| --- | --- | --- | --- |
| 1 | `Stack` > `Offstage` > `Padding` > `Column` | `Tried to build dirty widget in the wrong build scope` → 이후 `Cannot hit test a render box that has never been laid out` 무한 반복 | ① 측정 콜백 안에서 `setState` 직후 `jumpTo`를 **즉시** 호출해 예약된 리빌드 위에 동기 리빌드를 겹침 ② `Stack`이 `Offstage` 자식까지 담으려 크기를 계산해 그림자가 시트를 밀어냄 |
| 2 | 위 + `jumpTo`를 `addPostFrameCallback`으로 지연 + 그림자를 `Positioned(top/left/right)`로 감쌈 | `RenderFlex overflowed by 471 pixels` | `Positioned`에 `bottom`을 안 줘도 높이 제약이 "0~무한대"가 아니라 **"0~Stack의 현재 높이"** 다. 시트가 접히면 Stack이 작아져 mid 그림자(471px)가 안 들어간다 |
| 3 | 위 + `OverflowBox(minHeight: 0, maxHeight: double.infinity)` | `RenderConstrainedOverflowBox object was given an infinite size during layout` + 여전히 471px overflow | `maxHeight: double.infinity`가 자식뿐 아니라 **`OverflowBox` 자신의 높이도** 무한대로 만든다. 화면에 무한대 높이 상자를 놓을 수 없다 |

`flutter analyze`는 세 번 다 **통과**했다. 컴파일 오류가 아니라 런타임 레이아웃 오류였고,
넓은 화면은 멀쩡한데 좁은 화면에서만 빨간 에러 화면이 무한 반복됐다.

**세 번째 실패에서 방법을 바꿨다.** 위젯 트리 안에 실물을 그려놓고 재려는 한, 그림자도
결국 부모의 크기 제약을 받는다. 그런데 재려던 값은 **전부 우리가 코드에 직접 써넣은 고정
숫자**였다 — 패딩 20/8/28, 여백 20/4/24/20/10, 구분선 1, 드롭다운 52. 그리지 않고 더하면 된다.

**3. 계산 방식의 유일한 단점을 상수 공유로 없앴다**

"콘텐츠 구성이 바뀌면 계산식도 같이 고쳐야 한다"가 계산 방식의 약점이다. 진짜 위험한 건
**둘이 다른 자리에 적힌 다른 숫자**라서 한쪽만 고쳐도 컴파일이 통과한다는 점이다.

```dart
static const double _gapBeforeMetrics = 20;
// build()  → const SizedBox(height: _gapBeforeMetrics)
// 계산식   → ... + _gapBeforeMetrics + ...
```

같은 상수를 양쪽이 읽으면 **어긋나는 것 자체가 불가능**해진다. 문구도 마찬가지로 상수화했다 —
문장이 길어지면 줄바꿈이 생겨 높이가 달라지기 때문이다.

`SurbiDropdown`에서는 메뉴 offset에 박혀 있던 `52`를 `collapsedHeight`로 승격했다.
`// 버튼 높이에 맞춰 조정`이라는 주석이 붙어 있던 것으로 보아, **원래 상수였어야 할 값이
주석으로만 존재하고 있었다.**

**4. `DraggableScrollableSheet`은 끌기와 휠을 다른 경로로 처리한다**

"mid에서도 스크롤되게 해서 업종을 고를 수 있게 하자"는 안이 나왔는데, SDK 소스를 먼저 읽고
갈렸다.

```dart
bool get listShouldScroll => pixels > 0.0;

void applyUserOffset(double delta) {
  if (!listShouldScroll && (!(extent.isAtMin || extent.isAtMax) || ...)) {
    extent.addPixelDelta(-delta, ...);   // 시트를 키운다
  } else {
    super.applyUserOffset(delta);        // 목록을 스크롤한다
  }
}
```

**목록이 맨 위이고 시트가 min도 max도 아니면 무조건 시트가 움직인다.** mid가 정확히 그
조건이라, 끌기로 mid에서 스크롤하는 것은 **구조적으로 불가능**하다. 이건 버그가 아니라
"카드 본체를 잡고 끌어올리기"를 성립시키는 그 위젯의 존재 이유다.

그런데 **마우스 휠은 `pointerScroll`이라는 다른 경로**를 타서 시트를 건너뛰고 목록을 그냥
스크롤한다. 실제로 휠로 테스트했을 때는 "스크롤되네?"로 보였다. 모바일 대상 화면인데
데스크톱 휠에서만 되는 동작을 설계 전제로 삼을 뻔했다.

해결은 스크롤이 아니라 **mid가 보여주는 범위를 드롭다운까지 넓히는 것**이었다. 계산해보면
시트 위끝에서 드롭다운 아래끝까지는 **351px로 고정**이다(콘텐츠 순서가 정하지 시트 크기가
정하지 않는다). 세로 700px 화면에서 아래로 남는 공간은 mid 28px · max 349px —
즉 mid에 무엇을 넣든 **아래로 펼칠 자리는 max에만 있다.** 그래서 메뉴는 mid에서 위로,
max에서 아래로 펼치게 했다. max에서 위로 펼치면 방금 읽던 지역 지표를 메뉴가 덮는다.

**5. ⭐ 계산이 8.6px 틀려 있었다 — 위젯이 실제로 쓰는 스타일은 내가 준 스타일이 아니었다**

계산 방식으로 바꾼 뒤에도 min에서 **미세하게 스크롤**되는 증상이 남았다. "신경 쓸 정도는
아니다"로 넘어가려다 원인을 봤더니 계산 오류였다.

`Text` 위젯은 우리가 준 `TextStyle`만으로 그리지 않는다. 주변 `Material`이 깔아둔
`DefaultTextStyle`(= `theme.textTheme.bodyMedium`)과 **병합해서** 그린다. Material 3의
bodyMedium에는 `height: 1.43`이 들어 있고 우리 스타일에는 `height`가 없으므로,
그 1.43이 그대로 살아남는다.

```
실제 제목 줄 높이 : 20 × 1.43   = 28.6px
측정한 줄 높이    : 20 × 약1.17 = 23.4px   (TextPainter가 폰트 기본값으로 계산)
→ 제목 5.2px + 부제 3.4px = 헤더 하나당 약 8.6px 부족
```

`Theme.of(context).textTheme.bodyMedium`을 꺼내 `merge`한 뒤 재도록 고쳤다.
`height`뿐 아니라 `letterSpacing: 0.25`까지 따라와 줄바꿈 판정도 정확해졌고,
**화면에 그려지는 결과는 하나도 바뀌지 않았다.**

**6. 지도 확대 leak — 늦는 방어와 안 늦는 방어**

시트 위에서 휠을 굴리면 지도가 함께 확대됐다. `_MapLockZone`(카카오맵 `setZoomable(false)`)
논리 자체는 8/21에 고친 그대로 멀쩡한데, **타이밍이 늦는다.**

```
브라우저 wheel 이벤트
  ├─① 카카오맵 DOM 리스너 실행   ← 이미 확대됨
  └─② Flutter가 위젯에 전달 → lockMap()
```

마우스를 움직여 들어오면 `onPointerHover`가 미리 잠그지만, 커서를 시트 위에 둔 채 휠만
굴리면 hover가 발생하지 않아 첫 틱이 그대로 샌다.

`pointer_interceptor`(flutter.dev)로 시트 뒤에 **투명한 DOM 조각**을 깔아 브라우저 단계에서
지도가 이벤트를 받지 못하게 했다. 경쟁에서 이기는 게 아니라 **경쟁 자체를 없애는** 접근이다.
`_MapLockZone`은 `Overlay`로 뜨는 드롭다운 메뉴 경로를 위해 남겨뒀다.

**7. min을 세 상태 공통으로 통일해 "구마다 다르게 동작하는 버그"를 미리 막았다**

설계 초안에서는 "①안내·②동 목록은 짧으니 level과 무관하게 전체를 보여준다"고 정했는데,
**②는 짧지 않다.** 강남구는 행정동이 22개다. 목록 전체를 min의 기준으로 삼으면 그 높이가
화면보다 커져 min·mid·max가 사실상 같아지고, **동이 많은 구에서만 시트가 안 접힌다.**
동이 적은 구에서는 재현되지 않는 형태의 버그다.

min을 세 상태 모두 "헤더만"으로 통일해 규칙 하나로 정리했다.

### 오늘 배운 것 / 느낀 점

- **같은 문제로 세 번 연속 실패했다면 네 번째 변형이 아니라 접근을 갈아야 한다.**
  세 번의 에러 메시지가 전부 달라서 매번 "이번 것만 고치면 된다"고 느꼈지만, 공통점은
  **"위젯 트리 안에서 부모 제약을 피하려 한다"** 하나였다. 에러가 다르다고 원인도 다른 건 아니다.

- **재려던 것이 원래 내가 적어둔 숫자라면, 재는 것 자체가 과잉이다.** 그림자 복사본은
  "모르는 값을 알아내는" 도구인데, 우리가 알고 싶던 값은 패딩과 여백처럼 이미 코드에
  있는 것들이었다. 문제를 푸는 방법을 고르기 전에 **문제가 정말 그 종류인지** 봐야 했다.

- **`flutter analyze` 통과 ≠ 앱 정상.** 레이아웃은 컴파일러가 안 봐주는 영역이다.
  세 번의 실패 모두 analyze는 통과했고 넓은 화면도 멀쩡했다. 좁은 화면에서만 죽었다.

- **위젯이 실제로 쓰는 스타일과 내가 넘긴 스타일은 다르다.** `Text`가 테마와 병합한다는 걸
  몰라서 8.6px이 틀렸다. 앞으로 무언가를 코드로 재려 할 때는 **"그려질 때 무엇이 더 붙는가"**
  를 먼저 확인해야 한다.

- **"신경 쓸 정도 아닌 증상"이 계산이 틀렸다는 유일한 신호였다.** 미세 스크롤을 그냥 넘겼으면
  8.6px 오차는 그대로 남았고, 나중에 글꼴 배율이 큰 기기에서 헤더가 잘렸을 것이다.
  8/23에 "로그는 화면이 못 보여주는 것을 본다"고 적었는데, 이번엔 **작은 증상이 그 역할**을 했다.

- **조작 방식을 구분하지 않고 "되네?"를 받아들이면 위험하다.** 모바일 대상 화면을 데스크톱
  마우스 휠로 검증하고 있었다. SDK 소스를 먼저 읽지 않았으면 터치에서 성립하지 않는 동작을
  전제로 설계를 짰을 것이다.

- **방어에는 타이밍이 있다.** `lockMap`은 "지도한테 잠깐 눈 감으라고 부탁"하는 방식이라 늦을
  수 있고, `PointerInterceptor`는 "유리판을 덮는" 방식이라 안 늦는다. 8/20에 `setZoomable`로
  정면 해결했던 그 방법이 **다른 입력 경로에서는 부족했다** — 같은 문제라도 들어오는 길이
  달라지면 해법도 다시 골라야 한다.

- **틀려도 안 죽는 구조를 고르는 것도 설계다.** 최종 구조는 시트 안이 `ListView` 한 겹뿐이라,
  계산이 작으면 살짝 스크롤되고 크면 살짝 여백이 남을 뿐 overflow가 날 수 없다.
  §4에서 세 번 터진 것이 전부 `Column`을 제약 걸린 자리에 둬서 생긴 overflow였다.

- **"내 화면에선 안 나는 조건"을 코드에 남겨야 한다.** 시트 영역 640px 미만에서 업종 메뉴가

  ⚠️ 주석과 미해결 12번으로 남겨, 팀이 실기기로 테스트했을 때 "왜 잘려?"의 답이 코드 안에 있게 했다.

**6. 지도가 시트에 가려진 만큼을 계산에 넣었다**

`setBounds`가 **시트 뒤에 숨은 영역까지 포함한 한가운데**에 대상을 놓고 있었다. 서울 전역도,
선택한 동도 시트 뒤로 내려갔다. 카카오맵 `setBounds`는 패딩 4개를 더 받는데
`kakao_map_interop.dart`에 인자 1개짜리로만 선언돼 있어서 쓸 수 없던 것이었다.

```dart
@JS('setBounds')
external void setBoundsWithPadding(KakaoLatLngBounds bounds,
    int paddingTop, int paddingRight, int paddingBottom, int paddingLeft);
```

⚠️ 처음엔 가려지는 양을 **mid 고정**으로 넣었는데, 시트를 min으로 접어둔 상태에서도 화면
절반을 비워두게 되어 지도가 절반 크기로 축소됐다. **"덮여 있다"는 사실은 지금 시트가 얼마나
큰지에 달렸다** — 현재 크기를 쓰되 0.55로 상한을 뒀다.

**7. 시트 크기와 내용이 어긋나는 버그 2건을 잡았다**

- **`snapSizes`를 getter로 만들면 안 된다** — 매 build마다 새 리스트가 만들어져
  `didUpdateWidget`의 정체 비교에 걸렸다. 내부 extent가 통째로 교체되면서 크기가
  `initialChildSize`로 되돌아갔는데, 그 되돌림은 리스너를 울리지 않아 단계는 그대로 남았다.
  **크기는 mid인데 내용은 min**. 화면을 아무 데나 눌러 rebuild가 일어나야 맞춰졌다.
  결정적 단서는 "**바텀시트 영역 누르면 동목록이 나타나**"였다.
- **넓은 화면에 갔다 오면** 시트가 통째로 새로 만들어져 첫 build 시점엔 컨트롤러가 아직
  안 붙어 있다. 거기서 단계 재판단을 건너뛰면 떠나기 전 단계가 남는다.
  `initialChildSize`에 계산값(`_sheetMidFraction`)을 넣은 것도 같은 재설정을 유발해,
  고정 상수 `_sheetInitialSize`로 분리했다.

**8. `AI 창업 점수 보기` 버튼을 스크롤 밖 고정 푸터로 뺐다**

CTA가 `ListView` 안에 있으면 스크롤 한 번에 화면 밖으로 사라진다. 손잡이를 `ListView`
밖으로 뺀 것과 같은 논리로 시트 하단에 고정했다. 부수 효과로 **상태 ③(동 선택 후)의 mid가
①②보다 낮던 문제**도 함께 풀렸다 — 푸터 높이가 상수로 mid 계산에 더해지면서 정렬됐다.

**9. 그 직후 생긴 버그 2건 — 원인은 조건부 `return` 하나였다**

푸터를 넣자 두 증상이 나타났다.
- 탭으로 `max → mid → min → mid`를 돌면 시트가 중간 높이에 멈췄다. 단계는 가까운 곳(mid)으로
  판정되니 내용은 mid인데 높이가 모자라 **드롭다운만 잘리고 CTA는 보였다.**
- 같은 경로를 드래그하면 시트가 **덜덜 떨렸다.**

높이 계산(`measureStops`)도 정지 위치 재정렬(`_applyStops`)도 정상이었다. 범인은 `build()`가
돌려주는 **트리 모양**이었다.

```dart
if (!_hasFooter) return list;               // min  : ListView가 트리의 뿌리
return Column([Expanded(list), footer]);    // mid·max: ListView가 Column의 자식
```

`_hasFooter`가 `level != min`에 걸려 있어서, **min 경계를 넘을 때마다 ListView가 트리에서
자리를 옮겼다.** Flutter는 자리가 바뀐 위젯의 `Element`를 재사용하지 못하고 새로 만들며,
그때 매달려 있던 `ScrollPosition`도 함께 버려진다.
`DraggableScrollableController.animateTo`는 **그 `ScrollPosition` 위에서 돌아가는
활동(activity)** 이라, 위치가 갈리는 순간 애니메이션이 중단된다. 드래그는 `jumpTo`가
프레임마다 불리므로 같은 일이 반복돼 진동으로 보였다.

해결은 **자리를 지키고 내용만 비우는 것**이었다.

```dart
Column(children: [
  Expanded(child: list),
  if (_hasFooter) Padding(padding: footerPadding, child: _ScoreButton(...))
  else const SizedBox.shrink(),
]);
```

### 오늘 배운 것 / 느낀 점

- **"통일"은 값을 맞추는 일이 아니라 값을 한 곳에 모으는 일이다.** 색을 하나하나 같게
  고쳤다면 다음 화면을 만들 때 또 어긋났을 것이다. 토큰으로 모으고 나니 그 뒤로는
  화면 파일을 열 이유가 없어졌다.

- **`grep`은 "틀린 색"은 찾아도 "빠진 색"은 못 찾는다.** 하드코딩된 `0xFF...`는 전부 잡혔지만,
  애초에 색을 지정하지 않아 M3 기본값으로 나오던 곳(뒤로가기 버튼의 회색 hover)은
  검색으로 걸리지 않았다. **검색은 있는 것만 본다** — 없는 것을 찾으려면 화면을 봐야 한다.

- **`Colors.transparent`는 색이 아니라 "그리지 마라"는 뜻이다.** 색 일괄 치환 중에 선택
  안 된 탭의 밑줄 색을 회색 토큰으로 바꿨더니, 없던 선이 전 탭에 생기고 구분선과 겹쳐
  이중선이 됐다. **투명은 회색의 옅은 버전이 아니다.**

- **주석과 코드가 어긋난 곳을 오늘만 다섯 군데 찾았다.** "화면 크기를 통일"이라 적힌 옆에
  1200이 박혀 있고, 파일 헤더가 옛 파일명을 가리키고, "더 은은하게"라고 적힌 값이 기준의
  두 배였다. **주석은 코드와 함께 안 고치면 거짓말이 된다** — 다음 사람이 코드를 안 읽고
  주석을 믿으면 그때부터 진짜 버그가 된다.

- **위젯이 트리에서 '자리를 옮기는 것'만으로 상태가 죽는다.** Flutter를 배우며 위젯은
  "그리는 방법을 적은 설명서"라고 이해했는데, 그 설명서가 붙어 있는 **위치**가 상태의
  주소였다. 주소가 바뀌면 이사가 아니라 **철거 후 신축**이다.

- **성격이 다른 두 버그가 사실 하나였다.** 탭할 때의 "멈춤"과 드래그할 때의 "떨림"은
  증상만 보면 전혀 다르지만, 둘 다 min 경계에서 일어났고 원인이 같았다.
  **증상을 세는 게 아니라 발생 지점을 세야 했다.**

- **커밋을 나누는 게 항상 옳지는 않다.** 푸터 도입분이 아직 커밋되지 않은 상태였으므로
  `feat`/`fix`로 나누면 **고장난 상태를 히스토리에 일부러 한 칸 남기게 된다.**
  커밋 분리는 *이미 각자 동작하는* 변경끼리 성격이 다를 때 쓰는 도구다.

  택한 이유는 단계가 많아지면 "어느 걸 쓰지?"라는 판단이 매번 되살아나기 때문이다.
- 손으로 그리던 카드 2곳(`report_viewer`·`score_hub_panel`)을 `SurbiCard`로 교체.
  같은 카드인데 그림자 농도가 **0.1 vs 0.05로 갈려** 있었고, 진한 쪽 주석은
  "배경이 흰색이 아니니 그림자도 더 진하게"였다 — **주석과 값이 반대**였다.
- `report_viewer`의 아이콘 배경 원이 `bgColor`(= 카드 배경과 동일)라 **보이지 않는
  상태**였다. 주석의 의도("흰색으로")대로 고쳤다.

**2. AppBar 재정비 — 오전 결정을 두 번 뒤집었다**

오전에 "AppBar 배경을 본문과 같은 `primary`로 통일 · 구분선 제거"를 했는데,
실물을 보니 **바가 본문에 녹아 어디까지가 바인지 안 보였다.** 되돌렸다.

통일해야 할 대상을 잘못 잡은 것이다 — **"같은 색"이 아니라 "같은 규칙"**이었다.
새 규칙: *상단 바는 어느 화면에서든 본문(#F8FAFA)보다 한 톤 밝은 순백이고,
아래에 1px 구분선을 둔다.* `SurbiAppBar`와 `ExploreTopBar`에 동일 적용.

제목 크기도 하루에 **18 → 20 → 16**으로 두 번 옮겼다.
- 20으로 올린 근거: "화면 제목이 카드 제목(16)보다 커야 한다"
- 16으로 내린 근거: 드롭다운 글자와 **같은 자리·같은 역할**이므로 맞춰야 한다.
  위계는 크기가 아니라 **위치(바 안 vs 카드 안)와 그 사이의 구분선**이 이미 만든다.

**3. 뒤로가기 버튼을 `SurbiBackButton` 하나로 합쳤다**

`SurbiAppBar`와 `ExploreTopBar`가 각자 IconButton을 만들어 쓰면서 아이콘 종류
(`chevron_left` vs `_rounded`) · 크기(30 vs 28) · hover 원의 색과 크기 · 왼쪽
여백(28px vs 36px)이 **전부 갈려** 있었다. 속성을 하나씩 대조해 맞추는 대신
위젯으로 합쳐 **맞출 것 자체를 없앴다.**

이 과정에서 두 가지를 배웠다 (상시 규칙으로 승격).
- **`Theme`은 명령이 아니라 상속이다** — `main.dart`의 `iconButtonTheme`이
  AppBar 안까지 닿지 않았다. AppBar가 자기 `IconButtonTheme`을 더 가까이 씌운다.
- **tight 제약 앞에서 `fixedSize`는 무시된다** — AppBar가 leading을 72×76으로
  늘려 hover 원이 48이 아니라 72로 그려졌다. `Center`+`SizedBox`로 한 겹 감싸
  제약을 껍데기에서 끊었다.

**4. 흰 바 위에서 드롭다운이 사라졌다**

바를 순백으로 바꾸자 흰 알약이 바에 녹았다. **면 색을 바꿔 해결하지 않았다** —
이 드롭다운은 바탕이 다른 두 곳(상단 바 #FFFFFF / 하단 시트 #F8FAFA)에 살기
때문에 **어느 한 색으로 채워도 둘 중 한 곳에서는 묻힌다.** 선은 둘 다에서 성립한다.

⚠️ 테두리를 넣자 높이가 52 → 54가 됐다. `Container`의 `border`는 안쪽으로 패딩을
밀어넣기 때문이다. 세로 패딩을 14 → 13으로 줄여 52를 지켰다 — 안 줄였으면 하단
시트 mid 계산이 조용히 2px 어긋났을 것이다.

**5. 상단 바 높이 통일 (57 vs 77)**

`SurbiAppBar`는 `kToolbarHeight`(56)+선, `ExploreTopBar`는 패딩12+드롭다운52+패딩12+선.
**낮은 쪽에 맞추지 않았다** — 56에 52짜리 드롭다운을 넣으면 여백이 2px밖에 안 남는다.
**내용이 있는 쪽이 높이를 정한다.** `SurbiBar` 규격을 만들어 둘이 같은 값을 읽게 했다.

**6. `lib/` 전체 재스캔 — grep이 못 보는 결함을 찾았다**

`explore_panel.dart`가 C차 대상 14개에서 빠져 있었다(그 시점에 이미 커밋된 파일이라
변경 목록에 안 잡혔다). 훑어보니 사다리 밖 값이 4개 더 있었다.

그리고 **`TextStyle`인데 `fontSize`가 없는 곳 8개**를 스크립트로 찾아냈다.
이건 grep으로 못 찾는다 — '틀린 값'이 아니라 '없는 값'이라서다.
그중 6곳만 고치고 5곳은 그대로 뒀다. 판단 기준은 상시 규칙에 정리했다.

**7. 마무리 다듬기 — 드롭다운 강조 · 목록 행 그림자 · 화살표 색**

- 드롭다운의 **고른 값**을 `SurbiAppBar` 제목과 완전히 같은 스타일(16·w600·네이비)로.
  힌트는 회색 보통 굵기로 남겨 "비어 있음 vs 채워짐"이 색+무게 두 채널로 갈리게 했다.
- 동 목록 행이 밋밋한 문제를 **볼드가 아니라 그림자**로 풀었다. 볼드는 이미
  "지금 고른 값"이라는 뜻을 갖고 있어서 22개에 쓰면 그 뜻이 사라진다.
  `SurbiShadow.card`(번짐 12)를 간격 6px 목록에 쓰면 그림자가 옆 행에 올라타므로
  `SurbiShadow.row`(번짐 6)를 신설했다.
- 드롭다운 화살표가 글자 색을 따라가게 했다. 동 목록 `>`는 네이비로 가지 않고
  `placeholderGray` → `textGray`로만 올렸다 — **22개는 개수가 무게를 곱한다.**

### 오후에 배운 것 / 느낀 점

- **"통일"은 생김새가 아니라 규칙을 맞추는 것이다.** 오전에 상단 바 색을 본문과
  같게 만들어 "통일"했는데, 통일은 됐지만 바가 사라졌다. 맞춰야 했던 건 색이
  아니라 *"바는 본문보다 한 톤 밝다"* 는 규칙이었다. 같은 이유로 드롭다운의
  윤곽선을 동 목록에 복사하지 않았다 — **문제를 푼 해법을 문제가 없는 곳에
  옮기면 그건 규칙이 아니라 장식이다.**

- **오전의 나와 오후의 나가 다투는 게 정상이다.** 오늘 AppBar 제목 크기를 두 번,
  배경색을 한 번 뒤집었다. 처음엔 "왜 자꾸 번복하지" 싶었는데, 근거가 없어서
  바꾼 게 아니라 **실물을 보고 근거가 갱신돼서** 바꾼 것이었다. 중요한 건
  번복하지 않는 게 아니라 **번복한 이유를 코드에 남기는 것**이다.
  주석에 "8/26에 18→20→16으로 두 번 옮겼다"와 그 근거를 적어뒀다.

- **검색은 있는 것만 본다.** 하루 종일 나를 문 결함 두 개(`fontSize` 미지정,
  `surfaceTint` 누락)가 전부 "없는 것"이었다. `grep`으로 하드코딩을 0으로 만들고
  "끝났다"고 두 번 선언했는데 두 번 다 틀렸다. **없는 것을 찾으려면 구조를 파싱하는
  스크립트를 짜거나 화면을 봐야 한다.**

- **값이 비슷하다고 합치면, 한쪽을 고칠 때 다른 쪽이 망가진다.** 오늘 회색이 셋,
  그림자가 둘이 됐다. 늘린 게 아니라 **갈라져 있던 걸 발견한 것**이다. 기준은
  "값이 비슷한가"가 아니라 **"쓰이는 모양이 같은가"** 다. 긴 직선과 짧은 곡선,
  넓은 카드와 촘촘한 행은 같은 값을 쓸 수 없다.

- **신호가 되려면 신호가 아닌 상태가 있어야 한다.** "동 목록도 볼드로 할까?"라는
  질문에 반대한 이유다. 볼드가 "고른 값"을 뜻하게 된 순간, 전부 볼드로 만들면
  그 뜻이 사라진다. 강조는 **강조하지 않은 것이 있을 때만** 강조다.

- **반복은 무게를 곱한다.** 드롭다운 화살표 2개를 네이비로 하는 것과 동 목록
  화살표 22개를 네이비로 하는 것은 전혀 다른 결정이다. 요소의 무게를 올릴 때는
  **그게 화면에 몇 개 나오는지**를 먼저 세야 한다.

- **속성 목록 두 벌을 손으로 맞추면 언젠가 갈린다.** 뒤로가기 버튼이 그랬다.
  "같은 숫자를 두 군데 적지 않는다"는 규칙이 숫자만이 아니라 **위젯에도 적용된다**는
  걸 배웠다. 맞춰야 할 것이 많아지면 그건 합쳐야 한다는 신호다.

- **팀원 제안에 5초 안에 반응하려면 값이 한 곳에 있어야 한다.** "회의 중에 바로
  보여주고 싶다"는 요구가 나왔는데, 오늘 토큰 작업 덕분에 `theme.dart` 한 파일과
  hot reload로 가능해졌다. 토큰화의 진짜 이득은 코드 정리가 아니라 **의사결정
  속도**였다.

### 겪었던 이슈들

**1. SDK 폴더 `Move-Item`이 "다른 프로세스에서 사용 중"으로 실패**
살아있는 `dart` 프로세스 5개가 SDK 폴더 내 파일 핸들을 쥐고 있었다. `Stop-Process`로 dart는
정리했지만 그래도 재시도가 막혔고, 결국 **재부팅**으로 해결했다. 8/20 집 PC 일지의 "누가
실행 중인가와 누가 파일을 쥐고 있는가는 다른 질문"이 이번엔 dart 자체였던 셈 — VS Code의
Dart Analysis Server가 백그라운드에서 물고 있었다.

**2. `flutter upgrade --force`가 `C:\flutter\bin\cache\dart-sdk` 이름 변경에서 액세스 거부**
`Move-Item`(단순 이동)은 됐지만, `upgrade`가 내부적으로 하는 새 폴더 생성·리네임은 막혔다.
**학교 PC의 `C:\` 루트 바로 밑은 일반 사용자 쓰기 권한이 제한**되어 있었던 것으로 보인다.
PowerShell을 **관리자 권한으로** 다시 열어 재시도하니 한 번에 통과했다.
→ **학교/회사 PC에서 `C:\` 루트 밑에 뭔가 설치·수정할 때는 관리자 권한을 먼저 시도**한다.

**3. PowerShell의 `where`는 `Where-Object`의 별명이라 파일 검색이 안 됨**
`where flutter`가 계속 빈 결과를 반환해 "PATH 등록이 안 됐다"고 오판할 뻔했다. 실제로는
`$env:Path`에 `C:\flutter\bin`이 정확히 들어있었다. PowerShell에서 파일을 찾을 땐
`Get-Command` 또는 `where.exe`(cmd의 진짜 `where`)를 써야 한다. **`where`라는 이름이
운영체제마다 다른 걸 가리킬 수 있다**는 걸 배웠다.

**4. ⭐ 새 환경에 저장소를 받으면 `flutter pub get`을 반드시 먼저 돌려야 한다**
SDK·git 설정을 다 맞춘 뒤 VS Code에서 프로젝트를 여니 `lib/` 전역 파일에서
`package:flutter/material.dart`조차 못 찾는다는 에러가 수백 건 쏟아졌다. 코드가 깨진 게
아니라 **이 저장소를 이 PC에서 처음 받았을 뿐이라 `.dart_tool/`·패키지 캐시 연결이 아직
없었던 것**이었다. `flutter pub get` 한 번으로 전부 해소됐다.
→ **§7 "작업 재개 시 첫 5분 체크리스트"에 이 스텝이 빠져 있었다** — 지금까지는 항상 같은
PC에서 이어 작업해서 드러나지 않았을 뿐. 새 PC·새 clone 상황에서는 `core.autocrlf` 다음,
`git pull` 이전(또는 직후)에 `flutter pub get`이 필요하다.

### 오늘 배운 것 / 느낀 점
- **관리자 권한 문제와 파일 잠금 문제는 에러 메시지가 비슷해 보여도 해법이 다르다.**
  전자는 "액세스 거부"(권한), 후자는 "다른 프로세스가 사용 중"(잠금) — 메시지를 정확히
  구분해서 읽어야 헛다리를 안 짚는다.
- **명령어 이름이 같아도 셸이 다르면 다른 물건일 수 있다.** `where`는 cmd.exe의 파일 검색
  명령이지만 PowerShell에서는 `Where-Object`의 별명이다. 에러 없이 조용히 빈 결과만
  반환하는 게 가장 헷갈렸다 — 에러가 나면 오히려 원인을 빨리 찾는다.
- **환경 세팅 체크리스트는 "한 번도 안 해본 상황"을 가정하고 다시 검토해야 한다.** §7은
  "같은 PC에서 이어 하는 경우"만 검증된 순서였고, "새 PC에 처음 받는 경우"의 스텝
  (`pub get`)이 빠져 있었다.
