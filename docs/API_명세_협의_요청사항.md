## 1. 문서 목적과 보는 법

FE 화면 개발 과정에서 “확정 안 되면 다음 작업이 막히는” 항목만 모은 협의 요청 목록이다.

**보는 법**
1. §2-1에서 **본인 담당 항목만** 확인
2. 표의 “원하는 답변 예시” 형태로 회신 — 대부분 한 줄이면 충분할 것으로 예상됨
3. 맥락이 추가로 필요할 경우 §5 화면별 상세로 이동

**우선순위**
- 🔴 **P1** — 회신 없으면 해당 화면 작업이 **중단**됨
- 🟡 **P2** — 여유 있을 때 확인 (작업은 임시값으로 진행 가능)

### 3-1. 화면 플로우 순서 — 8/3 회의 확정

```
① 지역·업종 선택 → ② 지도(업소 분포) → ③ 상권 분석 → ④ AI 점수 허브
```

- **AI 점수 허브 = 점수 + LLM 보고서 + 정부지원사업 + 체크리스트**
- `3.4 Surbi 데이터 연동 구조 정리` 문서의 Step 표기와 다름
해당 문서는 **화면 순서가 아니라 데이터 제공 순서** 기준으로 이해 후 구현함
판단 근거 → Step 0에 `GET /api/categories`가 있고, 보고서 · 체크리스트 화면이 없음
**이 해석이 맞는지 확인 필요** — 아니라면 화면 구조 재작업 예정.
- **엔드포인트 설계는 3.4안을 그대로 반영** `/api/categories` · `/api/districts` · `/api/analysis` · `/api/scores` · `/api/supports`

### 3-2. 점수 산출 단위 — 행정동 + 업종 (ML · BE 7/27 확정)

- 건물 단위 → **행정동 + 업종 단위**로 변경
- 라우팅 `/step4/:buildingId` → `/score/:districtCode/:categoryCode`
- 지도는 “건물 선택”이 아니라 **“경쟁 업소 분포 확인”** 용도로 역할 축소
- `buildings` 테이블 부재(3.3 [BE] 8번)에 따라 FE 모델을 `Building` → `Business`로 재정의

### 3-3. FE 반영 완료 (2026-08-16)

**위 두 결정을 코드에 반영 완료**
- 라우팅 전면 교체, `Building` → `Business` 재정의, 상권 분석 화면 재설계
- 업종 코드를 CS코드 외식업 10종으로 교체, 행정동 코드 8자리로 통일

## 4. ⚠️ 가장 급한 것 — P1-1 배경 설명

> 이 항목 하나로 Step 4 화면의 존폐가 갈려 따로 떼어 설명함
> 

### 무슨 일이 있었나

2026-07-07 시점 DB 파트 문서를 근거로, FE에서 `scores`가 아래 10개 컬럼을 갖는다고 보고 Step 4 구현

```
total_score · population_score · sales_score · age_target_score
competitor_score · ml_sales_score · transport_score · rent_score
model_version · score_reason
```

그런데 최신 `4.0 ERD 설계`(07-20)와 ML `4.2`/`4.3`(08-12~15)에서는 **3개만** 존재

```
score · expected_sales · closure_risk
```

### 문제 발생

| 화면 요소 | 상태 |
| --- | --- |
| 종합 점수 게이지 | ✅ `score`로 유지 가능 |
| 예상 성과 카드 | ✅ `expected_sales` / `closure_risk`로 유지 가능 |
| **“점수 상세 분석” 카드 (막대 차트)** | ❌ **채울 데이터 없음** |
| **LLM 보고서 입력값** | ❌ `score_reason` 소멸 → P1-2 |

### 로직은 이미 존재함

ML `3.0 점수화` 문서(07-20)를 보면 조장 배점표 기준 5개 항목이 **실제로 계산되는 것으로 확인**

```python
유동인구_지수 = 생활인구_백분위 / 100 * 20
업종_소비력   = sales_score / 100 * 20
경쟁_강도     = (100 - 경쟁업체수_백분위) / 100 * 15
접근성        = 지하철_백분위 / 100 * 10
운영_안정성   = (100 - closure_risk_score) / 100 * 15
```

DB로 전달만 안 하고 있는 상태로 보임

### 요청

**이 5개 값을 `surbi_final_scores.csv`와 `predict.py` 반환값에 함께 실을 수 있는지** 확인 필요

| 답변 | FE 대응 |
| --- | --- |
| **가능** | Step 4 현재 구조 유지, 막대 차트에 5개 항목 바인딩 (작업량 小) |
| **불가** | “점수 상세 분석” 카드 제거 후 Step 4 재설계 (작업량 大, 일정 재산정 필요) |

> 💡 80점 만점(정책 지원 적합도 제외)이든 100점 재환산이든 **FE에서 어느 쪽이든 대응 가능**
다만 **어느 쪽인지는 확정이 되어야** 게이지 최대값을 고정할 수 있음

### 예상 증상

```python
def get_score_by_district(district_code: str, category_code: str)   # 인자는 str
    ...
    result_df["district_code"] == district_code                      # CSV는 int64
```

`surbi_final_scores.csv`의 `district_code`가 **int64**로 저장돼 있어, 문자열을 넘기면 pandas 비교가 전부 `False`가 됨

1. 1단계 `existing_result` → 빈 결과
2. 2단계 `area_codes` → 빈 배열
3. 결과: **모든 요청이 `{"score": None, ..., "source": "district_not_found"}` 반환**

### 함께 확인 요청

| # | 내용 |
| --- | --- |
| 1 | `district_code` dtype 통일 (`astype(str)` 또는 인자 타입을 int로) |
| 2 | 문서 호출 예시 `get_score_by_district("1168010100", ...)`의 코드가 **10자리 법정동코드** — 데이터는 전부 **8자리 행정동코드**라 이 예시로는 실패할 가능성이 있음 |
| 3 | 파일 행수가 **22,954행** — 문서엔 “22,418건”으로 되어 있어, 이상치 제거 **전** 버전으로 생성됐을 가능성 |
| 4 | `expected_sales` **0원 1,454건** (→ **P2-2**) |
| 5 | 행정동 **397개만** 존재 (전체 427개 중 30개 누락) — 의도된 것인지 (→ **P2-5**) |
