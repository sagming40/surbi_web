## 1. 문서 목적과 보는 법

FE 화면 개발 과정에서 "확정 안 되면 다음 작업이 막히는" 항목을 정리한 협의 요청 목록입니다.

**보는 법**
1. §2-1에서 **본인 담당 항목만** 확인
2. 표의 "원하는 답변 예시" 형태로 회신 (한 줄이면 충분한 항목이 대부분입니다)
3. 맥락이 더 필요하면 §5 화면별 상세로 이동

**우선순위 기준**
- 🔴 **P1** — 회신 없으면 해당 화면 작업이 **중단**됨
- 🟡 **P2** — 여유 있을 때 확인 (작업은 임시값으로 진행 가능)

## 4-1. 📢 확정 사항 통보 — 화면 플로우 순서

> 질문이 아니라 **공유**입니다. 다르게 알고 계셨다면 알려주세요.

**8/3 회의 결정 (대조표 안건 2)**
```
① 지역·업종 선택 → ② 지도(업소 분포) → ③ 상권 분석 → ④ AI 점수 허브
```
- **AI 점수 허브 = 점수 + LLM 보고서 + 정부지원사업 + 체크리스트** (7/13 회의 지시 ⑤로 확정된 구조)
- `3.4 Surbi 데이터 연동 구조 정리` 문서의 "Step 4 = 정부지원사업" 표기와 다릅니다.
  해당 문서는 **데이터 제공 순서** 기준으로 이해했는데 맞는지 확인 부탁드립니다.
- **엔드포인트 설계는 3.4안을 그대로 채택합니다** — `/api/categories`, `/api/districts`,
  `/api/analysis`, `/api/scores`, `/api/supports`

**안건 1(점수 산출 단위)도 확정 반영합니다**
- 건물 단위 → **행정동 + 업종 단위**
- 라우팅 `/step4/:buildingId` → `/score/:districtCode/:categoryCode`로 변경 예정
- 지도는 "건물 선택"이 아니라 **"경쟁 업소 분포 확인"** 용도로 역할 축소

## 4. ⚠️ 가장 급한 것 — P1-1 배경 설명

> 이 항목 하나로 Step 4 화면의 존폐가 갈려서, 따로 떼어 설명드립니다.

### 무슨 일이 있었나

2026-07-07 시점의 DB팀 문서를 근거로, FE는 `scores` 테이블이 아래 10개 컬럼을 갖는다고 보고 Step 4를 만들었습니다.

```
total_score · population_score · sales_score · age_target_score
competitor_score · ml_sales_score · transport_score · rent_score
model_version · score_reason
```

그런데 최신 `4.0 ERD 설계`(07-20)와 ML `4.2`/`4.3`(08-12~15)에서는 **3개만** 남아 있습니다.

```
score · expected_sales · closure_risk
```

### FE에 생기는 문제

| 화면 요소 | 상태 |
| --- | --- |
| 종합 점수 게이지 | ✅ `score`로 유지 가능 |
| 예상 성과 카드 | ✅ `expected_sales` / `closure_risk`로 유지 가능 |
| **"점수 상세 분석" 카드 (막대 차트)** | ❌ **채울 데이터 없음** |
| **LLM 보고서 입력값** | ❌ `score_reason` 소멸 → P1-4 |

### 그런데 로직은 이미 있습니다

ML `3.0 점수화` 문서(07-20)를 보면, 조장 배점표 기준 5개 항목이 **실제로 계산되고 있습니다.**

```python
유동인구_지수 = 생활인구_백분위 / 100 * 20
업종_소비력   = sales_score / 100 * 20
경쟁_강도     = (100 - 경쟁업체수_백분위) / 100 * 15
접근성        = 지하철_백분위 / 100 * 10
운영_안정성   = (100 - closure_risk_score) / 100 * 15
```

DB로 전달만 안 하고 있는 상태로 보입니다.

### 요청

**이 5개 값을 `surbi_final_scores.csv`와 `predict.py` 반환값에 함께 실어주실 수 있는지** 확인 부탁드립니다.

| 답변 | FE 대응 |
| --- | --- |
| **가능** | Step 4 현재 구조 그대로 유지, 막대 차트에 5개 항목 바인딩 (작업량 小) |
| **불가** | "점수 상세 분석" 카드 제거 후 Step 4 재설계 (작업량 大, 일정 재산정 필요) |

> 💡 참고: 80점 만점(정책 지원 적합도 20점 제외)이든 100점 재환산이든 **FE는 어느 쪽이든 대응 가능**합니다.
> 다만 **어느 쪽인지는 확정되어야** 게이지 최대값을 고정할 수 있습니다.

### 5-3. Step 3 [건물 탐색 — 지도]

> ⚠️ **이 화면은 전면 재검토 대상입니다.**

DB `3.3` [BE] 8번·10번 답변에 따르면
- `buildings` 테이블 **없음** (`businesses.building_name` 컬럼만 존재)
- 건물별 개별 점수 **불가** (ML 점수는 행정동+업종 단위)

현재 FE는 "건물 마커 → 건물별 점수 미리보기 → `/step4/:buildingId`" 구조로 구현돼 있어, 대응 데이터가 없습니다.

**P1-3 — 아래 중 어느 방향인지 결정 부탁드립니다.**

| 안 | 내용 | FE 영향 |
| --- | --- | --- |
| **A안** | 건물 → **업소(businesses)** 단위로 재정의. 마커 = 해당 동+업종의 실제 점포들 | 라우팅 파라미터가 `:buildingId` → `:districtCode`+`:categoryCode`로 변경. 오버레이 카드 항목 재구성. 지도·마커·이벤트 로직은 **재사용 가능** |
| **B안** | 건물 개념 유지 → 건축물대장 API 신규 연동 | 일정 리스크 큼. BE 작업량 판단 필요 |
| **C안** | Step 3 자체를 축소/폐지하고 Step 2 → Step 4 직결 | 라우팅 단순화, 기존 Step 3 작업 폐기 |

> 💡 FE 의견: **A안 선호**. `3.2 DB 조회 결과 정리`에 이미 좌표 포함 쿼리가 검증돼 있고(왕십리도선동 카페 59개),

> 협의 항목은 아니지만, 그대로 배포되면 **모든 점수 조회가 실패**할 수 있어 함께 전달드립니다.

### 증상 예상

```python
def get_score_by_district(district_code: str, category_code: str)   # 인자는 str
    ...
    result_df["district_code"] == district_code                      # CSV는 int64
```

`surbi_final_scores.csv`의 `district_code`가 **int64**로 저장돼 있어, 문자열을 넘기면 pandas 비교가 전부 `False`가 됩니다.

1. 1단계 `existing_result` → 빈 결과
2. 2단계 `area_codes` → 빈 배열
3. 결과: **모든 요청이 `{"score": None, ..., "source": "district_not_found"}` 반환**

### 함께 확인 부탁드릴 것

| # | 내용 |
| --- | --- |
| 1 | `district_code` dtype 통일 (`astype(str)` 또는 인자 타입을 int로) |
| 2 | 문서 호출 예시 `get_score_by_district("1168010100", ...)`의 코드가 **10자리 법정동코드** — 데이터는 전부 **8자리 행정동코드**라 이 예시로는 실패합니다 |
| 3 | 파일 행수가 **22,954행** — 문서엔 "22,418건"으로 되어 있어, 이상치 제거 **전** 버전으로 생성됐을 가능성 |
| 4 | `expected_sales` **0원 1,454건** — 음수 보정 결과로 보이나, 화면 노출 시 처리 방침 필요 (**P2-2**) |
| 5 | 행정동 **397개만** 존재 (전체 427개 중 30개 누락) — 의도된 것인지 (**P2-3**) |
